# 실시간 게임 & 소셜 플랫폼 "Supershy"

## 프로젝트 소개

브라우저 기반 실시간 멀티플레이어 Pong 게임과 친구·채팅·토너먼트 기능을 제공하는 소셜 게이밍 플랫폼입니다. 마이크로서비스 아키텍처(MSA)를 채택하여 전체 서비스를 `Frontend`, `API Gateway`, `User`, `Game`, `Chat` 서비스로 분리하고, WebSocket + Redis로 저지연 상호작용을 보장합니다. 각 서비스는 Docker로 컨테이너화 되며 docker-compose로 관리됩니다.

## 프로젝트 목표

실시간 멀티플레이어 게임과 채팅 기능을 제공하는 확장 가능하고 안정적인 웹 플랫폼을 구축합니다. 이 문서는 프로젝트에 적용된 핵심 기술과 기능에 대한 저의 고민과 선택, 그리고 그 결과를 담은 기술 중심의 포트폴리오입니다.

## 핵심 기술 키워드

- **MSA(마이크로서비스), Database-per-service**
- **Nginx API Gateway, Reverse Proxy, SSL Termination**
- **WebSocket, Django Channels, ASGI/WSGI, Redis Channel Layer(Pub/Sub)**
- **JWT 인증/인가, Access/Refresh Token, 커스텀 미들웨어**
- **RESTful API 표준화**
- **Docker, docker-compose**

## 프로젝트에서의 역할과 핵심 기여

### 1. 마이크로서비스 아키텍처 (MSA) 설계 및 구축

- **역할:** 전체 서비스 경계 정의와 아키텍처 설계를 주도했습니다. `사용자(User)`, `게임(Game)`, `채팅(Chat)`의 도메인을 분리하고, 각 서비스의 독립성을 고려하여 Database-per-service 원칙을 적용했습니다. 또한 Nginx 기반의 `API Gateway`를 앞단에 배치하여 각 서비스로의 요청을 라우팅하였습니다. 인스턴스 확장성과 종속성을 고려하여 각 서비스를 Docker로 컨테이너화하고 `docker-compose.yml`로 통합 실행 환경을 구성했습니다.

- **문제 정의:** 초기 설계 단계에서 트래픽이 서비스 간에 전이될 위험과 작은 변경이 전체 배포로 이어질 위험을 식별했습니다. 또한 공유 DB 사용 시 스키마 변경 파급과 서비스별 독립 확장 한계가 발생할 수 있다고 판단했습니다.

- **의사결정 및 고려:** 모놀리식 대비 변경 독립성과 예상 트래픽 기준 도메인 분리를 최우선으로 두었습니다. 서비스 간 결합도를 낮추기 위해 공유 DB를 지양하고, 공용 스키마 변경의 파급효과를 차단했습니다. 서비스 간 통신은 gRPC도 검토했으나, 팀 생산성과 디버깅 용이성, 관측성 확보를 이유로 표준 REST를 채택했습니다. 독립 DB에서의 외래키 참조 불가로 인한 데이터 무결성 문제를 해결하기 위해 애플리케이션 계층에서의 처리를 고려하였습니다.

- **구현:**

  1.  **도메인 분리:** 각 서비스가 자체 비즈니스 로직과 데이터베이스를 소유하도록 설계했습니다.
  2.  **통신 표준화:** 서비스 간 호출을 REST로 통일하여 독립성과 일관성을 유지했습니다.
  3.  **환경 격리:** 모든 서비스를 Docker 컨테이너로 구성하고 `docker-compose.yml`로 일괄 관리했습니다.
  4.  **서비스 간 호출 예시:** `게임` 서비스에서 유저 랭킹 업데이트 시 `사용자` 서비스의 `api/user/{user_id}/` 엔드포인트를 호출하도록 설계했습니다.

- **성과:**
  - **독립적 확장성 확보:** 게임 트래픽 급증 시에도 `Chat`/`User`에 영향 없이 필요한 서비스만 수평 확장할 수 있게 했습니다.
  - **장애 전파 방지:** 서비스 경계를 통해 장애 격리가 가능해 가용성이 향상되었습니다.
  - **개발 생산성 향상:** 도메인별 병렬 개발이 가능해져 전체 개발 속도가 향상되었습니다.
  - **인스턴스 확장성:** 예상 트래픽 기준으로 도메인을 분리하여, 대용량 트래픽 발생 시에 트래픽이 몰리는 서비스만 수평 확장 가능하게 설계하였습니다.

### 2. WebSocket 기반 실시간 통신 시스템 구축

- **역할:** 실시간 통신 스택을 설계·구현했습니다. Django Channels를 도입하고, 다중 인스턴스 환경에서의 세션 분산 문제를 해결하기 위해 Redis 기반 Channel Layer를 구성했으며, 게임/채팅에 필요한 이벤트 프로토콜을 정의했습니다.

- **문제 정의:** 실시간 게임 특성상 폴링 기반 접근은 체감 지연과 불필요한 트래픽을 유발할 가능성이 높다고 판단했습니다. 또한 수평 확장 시 연결 분산으로 메시지 일관성이 깨질 수 있는 리스크를 사전에 인지했습니다.

- **의사결정 및 고려:** 폴링 대비 지연 시간과 서버 부하를 고려해 WebSocket을 채택했습니다. 인스턴스 스케일아웃 시 연결 일관성을 보장하기 위해 Pub/Sub 특성을 갖는 Redis를 선택했고, 이벤트 순서/유실 가능성에 대비한 최소한의 재전송/상태 동기 전략을 설계했습니다.

- **구현:**

  1.  **WebSocket 채택** 및 양방향 실시간 데이터 전송.
  2.  **Django Channels 적용**으로 WSGI/ASGI 공존 환경 구성.
  3.  **Redis Channel Layer**로 브로드캐스트와 인스턴스 간 메시지 동기화 구현.

- **성과:**
  - **평균 100ms 미만 지연:** 게임 오브젝트 상태와 채팅 메시지를 실시간 동기화해 끊김 없는 UX를 제공했습니다.
  - **수평 확장성:** 수백~수천 동시 연결을 안정적으로 처리할 수 있는 기반을 확보했습니다.

### 3. 분산 환경에서의 JWT 기반 통합 인증/인가

- **역할:** 인증을 `User` 서비스로 단일화하고 JWT 기반 토큰 체계를 설계·구현했습니다. 각 서비스 앞단의 커스텀 미들웨어에서 Access Token 검증 및 `user_id` 컨텍스트 주입을 담당하도록 했습니다.

- **문제 정의:** 마이크로서비스로 확장될수록 서비스별 인증 구현이 분산되어 정책 불일치와 권한 검증 중복이 발생할 위험을 확인했습니다. 인증 변경이 여러 저장소로 분산될 경우 수정 비용이 커질 수 있다고 판단했습니다.

- **의사결정 및 고려:** 인증 로직의 중복과 정책 불일치를 방지하기 위해 단일 진실 공급원(`User` 서비스)과 토큰 기반 전달을 선택했습니다. 토큰 만료/재발급 정책, 서비스 간 신뢰경계, 미들웨어 실패 시 폴백 전략 등을 고려했습니다.

- **구현:**

  1.  **인증 책임 분리:** `사용자` 서비스가 인증의 단일 공급원 역할 수행.
  2.  **JWT 발급:** 로그인 성공 시 Access/Refresh Token 발급.
  3.  **커스텀 미들웨어 인가:** 각 서비스 앞단에서 토큰 유효성 검증 및 `user_id` 기반 인가 수행. `CustomHttpMiddleware`를 구현하여 헤더의 Access Token을 검증하고 컨텍스트에 주입했습니다.

- **성과:**
  - **중앙화된 인증 관리:** 정책 변경이 한 곳에서 일어나 유지보수성이 향상됐습니다.
  - **느슨한 결합:** `게임`/`채팅`은 토큰 검증만 수행해 구현 의존도를 낮췄습니다.

### 4. Nginx 기반 API Gateway 구축

- **역할:** 단일 진입점으로서 Nginx 기반 API Gateway를 설계·구성했습니다. `nginx.conf`에 서비스별 라우팅 규칙을 정의하고, WebSocket 프록시와 SSL Termination을 설정했습니다.

- **문제 정의:** 클라이언트가 다수의 엔드포인트를 관리하게 될 가능성과 SSL·로깅·인증 같은 공통 기능이 각 서비스에 중복될 위험을 사전에 인지했습니다. WebSocket과 HTTP를 일원화할 단일 진입점이 필요하다고 판단했습니다.

- **의사결정 및 고려:** 별도 상용/오픈소스 게이트웨이 도입 대비 운영 복잡도와 성능을 고려해 Nginx를 채택했습니다. 공통 정책(인증/로깅/WS 처리)을 중앙화하면서도 각 서비스 변경과 독립적으로 운영될 수 있도록 구성했습니다.

- **구현:**

  1.  **리버스 프록시:** Nginx로 단일 진입점 구성.
  2.  **중앙 라우팅:** `location` 지시어로 URL 경로 기반 라우팅을 구성해 내부 `upstream`으로 전달.
  3.  **WebSocket 처리:** `Upgrade`/`Connection` 헤더 설정으로 WS 프록시 안정화.
  4.  **SSL 종료:** 게이트웨이에서 TLS 종료로 보안과 운영 효율성 향상.

- **성과:**
  - **클라이언트 단순화:** 프론트엔드는 게이트웨이 주소만 알면 됩니다.
  - **보안 강화:** 내부 네트워크 토폴로지를 은닉해 공격 표면을 축소했습니다.
  - **공통 정책 기반:** 로깅/레이트리밋 등 플랫폼 레벨 정책 적용 지점을 확보했습니다.

## 회고

- **기술적 성장:**

  - MSA에서의 분산 트랜잭션/장애 격리/관측성 과제를 직접 다루며 분산 시스템 설계의 복잡성과 중요성을 체득했습니다.
  - 비동기 프로그래밍과 WebSocket 실시간 처리 경험을 통해 대용량 트래픽에서의 실시간 아키텍처 설계를 경험하였습니다.

- **아쉬웠던 점 및 개선 방향:**
  - **동기 통신 의존:** 서비스 간 동기 REST 호출은 지연 전파 위험이 있습니다. Kafka를 활용한 이벤트 스트리밍 기반 비동기 통신을 도입하여 결합도를 더 낮추고 탄력성을 높이려 합니다.
  - **Kubernetes 오토스케일링:** 서비스별 부하 패턴에 대응하기 위해 Kubernetes 기반 오토스케일링을 적용하여 자동 확장/축소를 구현하고자 합니다.
